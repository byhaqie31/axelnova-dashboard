# Email Phase 2 — Credentials by Link, Not by Email

**Date:** 2026-10-12 · **Status:** Approved (owner answered the four decisions; "go directly", review after build) · **Branch:** `feat/email-phase-2-security` · **Builds on:** [2026-10-11-email-foundation-design.md](./2026-10-11-email-foundation-design.md) (Phase 1, live)

## 1. Problem

Today credentials travel in email and in queued-job payloads:

| Account | Today |
|---|---|
| Team (workspace) | The founder types/generates a password when creating a teammate; it is emailed in plaintext (`TeamWelcomeMail`) and shown on-screen once. Founder "Reset password" emails a new temporary password. "Forgot password" only notifies the founder. Nobody can set their own password. |
| Partner (referrer / investor) | An 8-digit passcode generated by the system, emailed in plaintext (`PartnerPasscodeMail`, sent synchronously so the passcode never enters the `jobs` table). "Forgot passcode" **rotates immediately** — anyone who knows a partner's email can lock them out. |
| Founder (cockpit) | No recovery path at all. |

## 2. Decisions (owner, 2026-10-12)

1. **Team "forgot password" is self-service:** the teammate gets a reset link directly; the founder gets a heads-up once the password is changed.
2. **Partners choose their own passcode** through a link (min 10 characters). Approval sends a set-up link; "forgot passcode" sends a reset link — nothing changes until the partner uses it, so nobody can lock them out.
3. **Set-up links** (new teammate's welcome, new partner's approval) are valid **72 hours**.
4. **Reset links** (team, partner, founder) are valid **60 minutes**.

Also (no decision needed): the founder gets **account recovery** — "Forgot password?" on the admin login emails a 60-minute reset link to the founder's own address.

## 3. Design

### 3.1 One-time access links

New table **`access_tokens`** — one row per issued link:

| Column | Notes |
|---|---|
| `account_type` | `user` · `external_account` |
| `account_id` | the account |
| `purpose` | `setup` (72h) · `reset` (60 min) |
| `token_hash` | SHA-256 of the 64-char random token, unique — the plaintext exists only in the email |
| `expires_at`, `used_at`, `created_at` | single use; expired or used links are refused |

Service **`App\Services\Auth\AccessLinks`**: `issue(account, purpose)` (invalidates that account's earlier unused links of the same purpose, returns the URL for the right surface), `inspect(token)` (valid? whose? which purpose?) and `redeem(token, secret)` (sets the password/passcode, marks the link used, signs the account out everywhere — all in one transaction). Lifetimes live in `config/auth.php` (`access_links.setup_hours = 72`, `access_links.reset_minutes = 60`).

Why not Laravel's password broker: it keys tokens by email in one shared table (a teammate and a partner can share an address), has one lifetime per broker, and doesn't cover the external-account guard cleanly. The custom table is small and covers all three surfaces with one model.

### 3.2 Endpoints

Public, in the login throttle group:
- `GET  /api/v1/auth/access-links/{token}` → `{ purpose, account: 'team' | 'founder' | 'partner', name, email }` or `410` (expired / used / unknown — one generic message).
- `POST /api/v1/auth/access-links/{token}` `{ secret, secret_confirmation }` → sets it (team/founder: min 12 chars; partner: min 10) and returns `{ login_url }`.
- `POST /api/v1/admin/forgot-password` (new) — founder accounts only; generic response.
- `POST /api/v1/team/forgot-password` — **now** emails the teammate a reset link (was: notify founder).
- `POST /api/v1/partner/forgot-passcode` — **now** emails a reset link (was: rotate immediately).

Founder-side changes:
- `POST /api/v1/admin/users` — **no `password` field**; the teammate gets a set-up link. The account is created with an unusable random password and `password_set_at = null`.
- `POST /api/v1/admin/users/{user}/reset-password` — sends a **set-up link** if the teammate never finished set-up, otherwise a **reset link**. Their current password keeps working until they choose a new one (deactivate the account to lock someone out). No password in the response.
- `POST /api/v1/admin/referral-partners/{p}/approve` and `/reset-passcode` — send a set-up / reset link; no passcode generated.

New column **`users.password_set_at`** (nullable; existing users backfilled to their `created_at`, since they already have passwords) — tells the Users screen whether to offer "Resend set-up link" or "Send reset link".

### 3.3 Emails (templates from Phase 1, copy updated)

| # | Type | Change |
|---|---|---|
| 18 | `partner.passcode` | "Set up your access" link (72h) instead of the passcode. Now queued. |
| 19 | `partner.reset_confirm` | "Choose a new passcode" link (60 min); ignore-if-not-you note. Now wired. |
| 20 | `team.welcome` | Warm welcome kept; "Set your password" link (72h) replaces the temporary password. |
| 21 | `team.password_reset` | "Choose a new password" link (60 min) for both self-service and founder-sent resets. Subject: "Reset your Axel Nova Ventures team password". |
| 26 | `partner.reset_alert` | Heads-up **after** a partner sets a new passcode through a reset link. |
| 27 | `team.reset_alert` | Heads-up **after** a teammate sets a new password through a reset link (subject "Team password changed — {name}"). |
| 32 | `admin.account_recovery` | Founder reset link (60 min). Now wired. |

No email carries a password or passcode any more, and every email is queued (the `PartnerPasscodeMail` exception from Phase 1 is gone). A link sits in the queue payload for seconds — short-lived and single-use, which is the standard trade-off.

### 3.4 Frontend

- **One shared component** `AccessLinkForm` (validate link → choose secret → confirm → link to sign-in), used by three pages that each keep their surface's look: `/team/set-password`, `/partners/set-passcode`, `/admin/reset-password` (all `?token=`).
- `/admin/forgot` (new) + a "Forgot password?" link on the admin login.
- `/team/forgot` and `/partners/forgot` copy updated ("we've emailed you a link").
- Admin Users: the create form loses the password field and the one-time credentials panel; "Reset password" becomes "Send reset link" / "Resend set-up link"; the detail page's one-time password reveal is removed.

### 3.5 Security notes

- Tokens: 64 random characters (`Str::random`), stored as SHA-256; single use; expired/used/unknown links get one generic answer.
- Redeeming a link revokes every Sanctum token of that account (signed out everywhere).
- Issuing a new link of the same purpose invalidates the account's earlier unused ones.
- Deactivated teammates and suspended partners can't redeem links; forgot-password responses stay generic (no account enumeration).
- Throttled like the login endpoints.

## 4. Testing

Backend: link lifecycle (issue → inspect → redeem; expiry; single use; reissue invalidates; wrong account type; deactivated account), each endpoint's behaviour and generic responses, founder-only admin recovery, sign-out on redeem, new user creation without password, founder reset choosing setup vs reset, partner approve/reset/forgot (no rotation), heads-up emails on completion only, email copy contains a link and never a password/passcode. Frontend: Vitest for any pure helpers; ESLint + typecheck.

## 5. Out of scope

Changing a password while signed in (profile page) — not requested; easy follow-up. Investor admin CRUD (still future work).
